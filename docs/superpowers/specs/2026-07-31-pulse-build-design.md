# Pulse Build Design — 2026-07-31

## What this document is

The product spec for Pulse lives in `Instructions/00_README.md` through `Instructions/10_DELIVERABLES.md` and is authoritative for features, screens, scoring math, colors, and copy. This document records the **build decisions and deliberate deviations** agreed with Joel on 2026-07-31 before implementation. Where this document is silent, the Instructions docs govern.

## Goal

Build the complete Pulse iOS + watchOS app from scratch for the Kaggle "Scripture in New Frontiers" competition (Wearables track), buildable from the CLI, deployable to Joel's physical iPhone and Apple Watch, and satisfying every item in the technical acceptance checklist in `Instructions/10_DELIVERABLES.md`.

## Deliberate deviations from the Instructions docs

1. **WidgetKit complications, not ClockKit.** Docs 06/09 specify `CLKComplicationDataSource`, which Apple deprecated. Complications are implemented as a WidgetKit extension using accessory families (`accessoryCircular`, `accessoryRectangular`, `accessoryInline`, `accessoryCorner`). Visual designs from doc 06 are preserved.
2. **`WKApplicationDelegate` / `WKApplication`, not `WKExtension`.** Modern watchOS lifecycle APIs; same background-refresh behavior as spec'd.
3. **`@Observable` view models** (doc 10's own quality standard) rather than the older `ObservableObject` shown in some code sketches in docs 03/04/06.
4. **API endpoint shapes are treated as illustrative, not literal.** The spec's Gloo endpoint (`POST /v1/scripture/contextual-verse`) and YouVersion endpoint (`GET /bible/verse`) were written before consulting the real docs. Both clients are built behind protocols (`VerseSelecting`, `VerseFetching`); the real endpoint contracts are taken from the current official Gloo AI Studio and YouVersion Platform documentation during the integration phase, with the spec's request/response *semantics* (state context in, verse reference out; reference + translation in, verse text out) preserved. If Gloo exposes only chat-style completions, the doc-04 system prompt is used with enforced JSON output.
5. **Mock health provider.** A `HealthDataProviding` protocol with two implementations: real HealthKit, and a mock that can simulate any of the 12 biometric states. The mock powers simulator runs, unit tests, and demo-video recording. Classification itself always runs the real scoring algorithm (doc 10 requires state classification not be hardcoded).

## Architecture (as agreed)

Three top-level components generated by XcodeGen:

- **Pulse** (iOS app): Onboarding, Home, History, Share, Settings features; HealthEngine (HealthKit observation + background delivery), ScriptureEngine (Gloo → YouVersion pipeline, cache, delivery scheduler), NotificationService, WatchConnectivity phone side, SwiftData persistence (`VerseDelivery`, `CachedVerse`, `UserPreferences`) in an App Group container (`group.com.joelroy.pulse`).
- **PulseWatch** (watchOS app) + **PulseWatchWidgets** (WidgetKit extension): vertical-page tabs (Verse, Vitals, History, Prayer), complications, haptics, WatchConnectivity watch side, background refresh.
- **PulseShared** (local Swift Package): `BiometricState` (12 states + display metadata + gradients), `HealthSnapshot`, `ClassificationResult`, `BibleVerse`, `WatchMessage` payloads, translation enum, design tokens (colors, typography, spacing, animations).

Data flow, scoring formulas, cooldown rules, and the fallback chain (Gloo → local reference map → cache → bundled `emergency_verses.json`) are implemented exactly as specified in docs 02–04.

## Error handling philosophy

- Missing health metrics render as "—", never as errors; classification tolerates nil fields via the completeness threshold (≥ 0.40).
- Every network failure falls through the fallback chain silently; the user always gets a verse.
- No force-unwraps in production paths; all async work via Swift Concurrency with timeouts.

## Testing

Test-first for logic layers, per doc 10: `StateClassifierTests` (all 12 states + fallback), `DeliverySchedulerTests` (cooldowns, quiet hours, urgency override), `HealthSnapshotTests` (completeness, sleep quality), `GlooAIClientTests` and `YouVersionClientTests` (mocked transport). UI is verified by building and running both apps in simulators, then on device.

## Build order

1. Toolchain + scaffold: XcodeGen install, `project.yml`, all targets compile empty.
2. `PulseShared` models + design tokens (tests).
3. Health engine: MetricCollector, SleepAnalyzer, StateClassifier, DeliveryScheduler (tests).
4. Scripture engine: real Gloo + YouVersion clients (docs consulted, keys from Joel), cache, orchestrator, fallback chain (tests).
5. Watch app: views, complications, connectivity, haptics.
6. iPhone app: design-system components, onboarding, home, history, share, settings.
7. Notifications, background tasks, phone↔watch sync end to end.
8. Phase 2 polish: Live Activities, breath prayer, streaks, sparklines, extra complication families.
9. Deliverables: README build instructions, SUBMISSION.md, screenshots; Kaggle rules compliance check at each milestone (https://www.kaggle.com/competitions/scripture-in-new-frontiers).

## Acceptance

Done when the technical acceptance checklist in `Instructions/10_DELIVERABLES.md` passes: both apps build and install on device, all 12 states classify from real HealthKit data without crashes, both APIs are called in the production flow with graceful fallback, at least 3 complication families show the current verse, and history/share/settings work end to end.
